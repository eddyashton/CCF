Scope the deep dive: JavaScript is not a sidecar or remote service. Each node embeds QuickJS in the process that executes C++ endpoints. The following slides trace interpreter construction, per-request capability binding, invocation, and cleanup.

01 / EXECUTION MODEL

JavaScript execution within a CCF node

01

Resolve the endpoint

The C++ registry reads endpoint metadata from KV to select an ES module and exported function.

02

Acquire a QuickJS context

The interpreter cache returns a fresh context or a context selected by the endpoint's reuse policy.

03

Bind this request

CCF attaches the current transaction, RPC context, request object, and application extensions.

04

Call JS and translate the result

The export returns { statusCode, headers, body }; CCF converts that object into the HTTP response.

02 / SAMPLE APPLICATION

programmability.cpp: registry structure

01

One registry serves both endpoint types

ProgrammabilityHandlers derives from DynamicJSEndpointRegistry, then registers ordinary C++ handlers in the same constructor. Dynamic JS lookup runs before the base registry falls back to those native definitions.

02

The application owns its JS storage

The namespace argument assigns this registry a set of KV maps for endpoint metadata, source modules, compiled bytecode, runtime options, audit records, and the interpreter flush marker.

03

The host can add narrower capabilities

The override of get_extensions() is called for each invocation. Here it creates MyExtension with a read-only pointer to the current transaction.

registry programmability.cpp
class ProgrammabilityHandlers : public
  ccf::js::DynamicJSEndpointRegistry
{
  ProgrammabilityHandlers(AbstractNodeContext& context) :
    DynamicJSEndpointRegistry(
      context, CUSTOM_ENDPOINTS_NAMESPACE)
  {
    make_endpoint(
      "/records/{key}", HTTP_PUT, put,
      {ccf::user_cert_auth_policy})
      .install();
  }
};
per invocation programmability.cpp / get_extensions
ccf::js::extensions::Extensions get_extensions(
  const EndpointContext& endpoint_ctx) override
{
  ccf::js::extensions::Extensions extensions;
  extensions.push_back(
    std::make_shared<MyExtension>(
      &endpoint_ctx.tx));
  return extensions;
}
This sample differs from a governance-installed JS app: it combines native and JavaScript endpoints, owns the policy for bundle installation, and adds a custom host extension. The underlying registry and interpreter paths are shared with standard JS applications.

03 / INITIALIZATION

Registry construction and interpreter factory

01

CCF asks the application for a registry

make_user_endpoints() is the application entry point. Each node constructs one ProgrammabilityHandlers instance during startup; this is registry setup, not interpreter creation.

02

The registry uses a node-wide cache

The base constructor retrieves AbstractInterpreterCache from the node context. Interpreters are requested lazily when a JS endpoint executes.

03

The factory installs reusable extensions

New contexts are CommonContext instances. Dependency-free APIs such as consensus and historical access are installed once here; transaction-bound extensions are added later for each request.

application entry programmability.cpp
std::unique_ptr<EndpointRegistry>
make_user_endpoints(AbstractNodeContext& context)
{
  return std::make_unique<
    programmabilityapp::ProgrammabilityHandlers>(
      context);
}
context factory src/js/registry.cpp
interpreter_cache = context.get_subsystem<
  AbstractInterpreterCache>();

interpreter_cache->set_interpreter_factory(
  [extensions](TxAccess access) {
    auto interpreter =
      std::make_shared<CommonContext>(access);

    for (const auto& extension : extensions)
      interpreter->add_extension(extension);

    return interpreter;
  });
Explain "setup" precisely: this call is CCF's app entry point. It constructs the endpoint registry; it does not eagerly create one interpreter per route. Interpreter contexts are acquired lazily during request execution from a node subsystem cache.

04 / APPLICATION UPDATE

Installing a JavaScript endpoint bundle

01

The sample owns admission policy

PUT /custom_endpoints authenticates an application administrator, optionally verifies a COSE timestamp, and records the action for ledger audit. Governance set_js_app uses the same bundle and runtime path; this sample moves admission into application space.

02

The bundle becomes replicated state

install_custom_endpoints_v1() replaces endpoint metadata and module source in namespaced KV maps. The transaction carries the same application definition to every node.

03

Existing contexts are invalidated

The installation writes the interpreter-flush map and regenerates QuickJS bytecode. A later cache lookup observes the new write version and discards contexts built for the old module graph.

05 / REQUEST EXECUTION

Per-request execution sequence

01

Acquire the appropriate context

The endpoint's transaction mode selects an application read-only or read-write context. Its reuse policy and the current flush marker determine whether the cache returns a warm context or constructs a fresh one.

02

Install this invocation's capabilities

CCF replaces the module loader, then attaches KV, RPC, request, and application-defined extensions. These objects contain pointers to the current transaction and RPC context.

03

Call one export, then detach

The registry resolves the configured ES-module export, creates its request object, applies runtime limits around JS_Call, and removes every request-local extension before interpreting the result.

acquire src/js/registry.cpp / do_execute_request
const auto rw_access =
  endpoint->properties.mode == Mode::ReadWrite ?
  TxAccess::APP_RW : TxAccess::APP_RO;

auto interpreter = interpreter_cache->
  get_interpreter(
    rw_access, reuse_policy, flush_marker);
auto& ctx = *interpreter;

std::lock_guard<ccf::pal::Mutex>
  guard(ctx.lock);
bind + invoke + detach src/js/registry.cpp
for (const auto& extension : local_extensions)
  ctx.add_extension(extension);

auto export_func = ctx.get_exported_function(
  *module_val, props.js_function, props.js_module);

auto val = ctx.call_with_rt_options(
  export_func, {request}, options, ...);

for (const auto& extension : local_extensions)
  ctx.remove_extension(extension);
Walk the sequence in order. The same Context object may survive, but its authority is refreshed per call. The context mutex serializes use because cached interpreters may be reused across threads. The module loader is also replaced for the current transaction.

06 / OBJECT LIFETIME

Interpreter context vs. request-scoped state

01

A cached context retains JavaScript state

The QuickJS runtime, global object, evaluated module graph, and any mutable globals can survive the request. CCF locks the context because a cached instance may be selected by requests on different threads.

02

Authority is attached for one invocation

KvExtension, RpcExtension, RequestExtension, and application extensions contain pointers into the current endpoint context. They are created after the context is acquired.

03

Extension lookup enforces the lifetime

After the call, CCF removes each extension instance from the context. A JS function object may still exist, but its native callback can no longer retrieve the removed capability or its stale transaction pointer.

request-local objects src/js/registry.cpp
ccf::js::extensions::Extensions local_extensions =
  get_extensions(endpoint_ctx);

local_extensions.emplace_back(
  std::make_shared<KvExtension>(
    &endpoint_ctx.tx, namespace_restriction));

local_extensions.emplace_back(
  std::make_shared<RpcExtension>(
    endpoint_ctx.rpc_ctx.get()));
bounded lifetime src/js/registry.cpp
for (const auto& extension : local_extensions)
  ctx.add_extension(extension);

auto val = ctx.call_with_rt_options(
  export_func, {request}, options, ...);

for (const auto& extension : local_extensions)
  ctx.remove_extension(extension);
Capabilities are ordinary C++ extension instances held by the Context. Their JS-visible properties may remain on globals, but after removal a host callback cannot resolve that extension instance. This prevents an old callback from carrying a stale transaction pointer into the next request.

07 / NATIVE EXTENSIONS

Registering MyExtension

01

Create a request-scoped capability

MyExtension carries a ReadOnlyTx*. The registry creates one for each invocation, so the API can read only from that request's transaction.

02

This C++ makes an object visible in JS

get_or_create_global_property("my_object", ...) creates the global object. Two calls to set() publish my_constant and hasRole on it.

03

JavaScript uses it like an ordinary global

Endpoint code can read my_object.my_constant and call my_object.hasRole(...). That function call crosses back into the C++ callback registered by new_c_function().

08 / QUICKJS C API

Native callback implementation requirements

01

The JS call enters the registered C function

my_object.hasRole(...) invokes js_has_role_permitting_action, the function pointer passed to new_c_function() on the previous slide.

02

Recover capability and convert arguments

The callback checks argc, recovers CCF's Context, retrieves this request's MyExtension, and converts QuickJS values to C++ strings.

03

Call native logic, then translate back to JS

The helper reads KV through extension->tx. Success becomes a JS Boolean; C++ exceptions become JS errors. This callback runs with native host privilege: QuickJS limits do not constrain defects here.

validate + recover programmability.cpp
JSValue js_has_role_permitting_action(
  JSContext* ctx, ..., int argc, JSValueConst* argv)
{
if (argc != 2)
  return JS_ThrowTypeError(ctx, ...);

auto& jsctx = *reinterpret_cast<
  ccf::js::core::Context*>(
    JS_GetContextOpaque(ctx));

auto* extension =
  jsctx.get_extension<MyExtension>();
if (extension == nullptr)
  return JS_ThrowInternalError(ctx, ...);
convert + return programmability.cpp
auto user_id = jsctx.to_str(argv[0]);
if (!user_id.has_value())
  return JS_ThrowTypeError(ctx, ...);

try
{
  const bool permitted =
    has_role_permitting_action(
      *extension->tx, user_id.value(), ...);
  return JS_NewBool(ctx, permitted);
}
catch (const std::exception& exc)
{
  return JS_ThrowInternalError(ctx, ...);
}
The interpreter protects native code from ordinary JS memory access, but a custom callback runs with the full privilege of the host process. Argument checking, conversion failures, C++ exception containment, and capability checks are all part of the sandbox boundary.

09 / INTERPRETER CACHE

Interpreter reuse policy and consequences

01

Reuse is selected by endpoint metadata

Without an interpreter_reuse policy, every invocation receives a fresh context. A key-based policy opts the endpoint into the node-wide LRU.

02

The effective key includes access mode

CCF appends (ro) or (rw) to the configured key. A context constructed for read-only transaction access cannot later be reused for a read-write endpoint.

03

Reuse changes observable semantics

Module evaluation and allocation are amortized, but globals and heap objects persist, memory remains resident, and requests sharing a key serialize on the context mutex. Correctness must not depend on a fresh global state.

cache key src/js/interpreter_cache.h
auto key = interpreter_reuse->key;
if (access == TxAccess::APP_RW)
  key += " (rw)";
else if (access == TxAccess::APP_RO)
  key += " (ro)";

auto it = lru.find(key);
if (it == lru.end())
  it = lru.insert(key, make_interpreter(access));
else
  lru.promote(it);
fresh by default src/js/interpreter_cache.h
if (interpreter_reuse.has_value())
{
  // KeyBased lookup returns a cached context.
  return it->second;
}

// No policy: construct but do not store.
return make_interpreter(access);
Reuse is opt-in through endpoint metadata. RO and RW contexts are separated. The mutex means reuse is cross-thread but not concurrently within one Context. Ask the audience: "Would this endpoint still be correct if globalThis.counter starts at 87?" If not, it should not rely on reuse.

if (cache_build_marker != freshness_marker) {
  lru.clear();

A marker change clears the complete LRU, so no cached module graph survives an application update.

The registry reads the version of the previous write to an interpreter-flush KV value. Any action modifying the app should update it. The cache compares this freshness marker on lookup and clears the whole LRU if it changed. Broad invalidation is simpler and safer than dependency-level invalidation.

Avoid claiming QuickJS alone is the sandbox. CCF's security posture is layered: embedded language isolation, explicit native extensions, KV namespace policy, endpoint authentication and transaction semantics, plus runtime resource bounds. There is no ambient Node.js capability set.
